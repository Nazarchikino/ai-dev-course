# ADR 0001: Зберігання бронювань у пам'яті процесу

- **Статус:** Прийнято
- **Дата:** 2025-12-15 (актуалізовано 2026-11-16)
- **Пов'язані модулі:** `src/bookings.js`, `src/app.js`, `data/rooms.json`

## Контекст

Сервіс `room-booking` розроблявся як легковаговий REST API для бронювання аудиторій коледжу, який використовується в навчальному процесі та має проходити швидке автоматизоване тестування (`npm test` виконується менш ніж за 1 секунду). Під час створення сервісу (версія `1.0.0` у `CHANGELOG.md`) необхідно було обрати спосіб зберігання списку аудиторій та активних бронювань так, щоб забезпечити ізоляцію тестових сценаріїв у `tests/api.test.js` і не ускладнювати розгортання проєкту на робочих станціях без додаткових серверів баз даних.

## Розглянуті варіанти

1. **Зберігання бронювань у пам'яті процесу (`in-memory` масив у замиканні `createBookingService`) + статичний JSON-файл `data/rooms.json` для довідника аудиторій.**
2. **Збереження бронювань у локальному JSON-файлі на диску (`fs.readFileSync` / `fs.writeFileSync`).**
3. **Вбудована реляційна база даних SQLite (`better-sqlite3` або `sqlite3`).**
4. **Зовнішня клієнт-серверна СКБД (PostgreSQL / MongoDB).**

## Рішення

Обрано **варіант 1**: довідник аудиторій зчитується зі статичного файлу `data/rooms.json` (або передається параметром у `createApp(rooms)`), а всі бронювання зберігаються в оперативній пам'яті всередині замикання функції `createBookingService(rooms)` у локальному масиві `const bookings = []` з автоінкрементним лічильником `let nextId = 1`.

## Обґрунтування

1. **Повна ізоляція тестів без очищення БД:** кожен виклик `createApp()` у `tests/api.test.js` створює новий незалежний екземпляр сервісу з порожнім масивом `bookings` і лічильником `nextId = 1`. Тести не впливають один на одного й не потребують `beforeEach`/`afterEach` для очищення таблиць чи файлів.
2. **Відсутність зовнішніх та нативних залежностей:** у `package.json` єдина runtime-залежність — `express`. Проєкт працює одразу після `npm install` на будь-якій ОС без встановлення СКБД чи компіляції C++ аддонів (як у випадку `better-sqlite3`).
3. **Простота та швидкість операцій:** обсяг бронювань у межах одного коледжу (десятки аудиторій, сотні записів) легко вміщується в оперативну пам'ять, де фільтрація `bookings.filter(...)` виконується за мікросекунди.

## Наслідки

### Позитивні
- Миттєвий запуск сервера та проходження всіх інтеграційних тестів (`< 1 с`).
- Проста фабрична архітектура (`createBookingService(rooms)`), зручна для модульного тестування та документування.

### Негативні та ризики
- **Втрата даних при перезапуску:** після завершення або перезапуску процесу Node.js усі створені бронювання зникають, а нумерація `id` починається з `1`.
- **Припущення:** неможливість горизонтального масштабування (запуску кількох воркерів через PM2 Cluster або кількох контейнерів за балансувальником навантаження), оскільки кожен процес матиме власний ізольований масив `bookings` і дозволить створити дублюючі бронювання на один і той самий час.
- **Припущення:** за тривалої безперервної роботи сервера без механізму архівації або очищення минулих дат масив `bookings` у пам'яті поступово зростатиме, уповільнюючи лінійний пошук `bookings.filter(...)` та `bookings.find(...)`.
- **Припущення:** повторно використані після перезапуску числові ідентифікатори (`id = 1, 2, ...`) можуть призвести до помилкового видалення іншого бронювання, якщо клієнт закешував старий `id` до перезапуску сервера.
