## Шаблон запиту
```text
Проаналізуй цей код як рецензент, що відповідає за безпеку.
Вимоги до API:
- POST /api/login: { login, password } → { token }; неправильні дані → 401
- GET /api/students?page=N: Сторінка з 5 студентів, page починається з 1; остання сторінка може бути неповною
- GET /api/students/search?name=...: Студенти, чиє ім’я містить рядок name; будь-які символи в name (зокрема апостроф) обробляються як звичайний текст
- GET /api/students/:id/average: { average } — середній бал, округлений до десятих; для студента без оцінок — { average: null }
- GET /api/students/:id/card: HTML-картка: ім’я, група, середній бал; для студента без оцінок — «оцінок немає»; дані виводяться як текст, а не як розмітка
- DELETE /api/students/:id: Лише для користувача з роллю teacher; без токена → 401, інша роль → 403; успіх → 204
- Будь-який маршрут: Некоректний :id → 400; неіснуючий студент → 404; внутрішня помилка → 500 без технічних подробиць
- Безпека: Паролі зберігаються лише як стійкий геш із сіллю. Секрети (ключ підпису токенів) не зберігаються в коді.

Код: [# файл]

Перевір окремо:
1. Обробку вхідних даних від користувача.
2. Формування запитів до бази даних.
3. Перевірку автентифікації та прав доступу.
4. Зберігання паролів і секретів.
5. Обробку помилок і те, що потрапляє у відповідь користувачу.
6. Логічні помилки та граничні випадки відносно вимог.

Для коїжної проблеми вкажи: рядок, суть, можливий наслідок, спосіб виправлення.
Якщо проблем у пункті немає – так і напиши.
```

## 1. Аналіз файлу `src/app.js`

1. **Обробка вхідних даних від користувача:**
   - **Рядок 43 (`GET /api/students/:id/card`):** поля `s.name` та `s.group_name` вставляються у HTML-відповідь без екранування (`<h1>${s.name}</h1><p>Група: ${s.group_name}</p>`).
   - **Можливий наслідок:** збережена XSS-атака (Cross-Site Scripting, OWASP A05:2025) — якщо ім'я або група студента містить `<script>...</script>`, браузер виконає скрипт; порушення вимоги «дані виводяться як текст, а не як розмітка».
   - **Спосіб виправлення:** створити функцію `escapeHtml(text)` для заміни `&`, `<`, `>`, `"`, `'` на HTML-сутності та застосувати її до `s.name` і `s.group_name`.

2. **Формування запитів до бази даних:**
   - Проблем немає (прямі SQL-запити у `src/app.js` відсутні, вони делеговані модулю `src/students.js`).

3. **Перевірка автентифікації та прав доступу:**
   - **Рядки 46–49 (`DELETE /api/students/:id`):** використано лише middleware `requireAuth`, але не перевіряється роль авторизованого користувача (`req.user.role`).
   - **Можливий наслідок:** порушення контролю доступу (OWASP A01:2025) — автентифікований користувач із роллю `student` може видаляти студентів із бази даних, отримуючи `204` замість `403`.
   - **Спосіб виправлення:** додати перевірку `if (req.user.role !== "teacher") return res.status(403).json({ error: "Доступ заборонено" });`.

4. **Зберігання паролів і секретів:**
   - Проблем немає безпосередньо в `src/app.js` (логіка автентифікації та секретів розміщена у `src/auth.js` і `src/config.js`).

5. **Обробка помилок і те, що потрапляє у відповідь користувачу:**
   - **Рядки 51–53 (`app.use((err, req, res, next) => ...)`):** глобальний обробник помилок повертає клієнту `{ error: err.message, stack: err.stack }`.
   - **Можливий наслідок:** витік внутрішньої технічної інформації (структура файлів, деталі СУБД SQLite, стек викликів), що суперечить вимозі «внутрішня помилка → 500 без технічних подробиць».
   - **Спосіб виправлення:** повертати узагальнене повідомлення `res.status(500).json({ error: "Внутрішня помилка сервера" })`.

6. **Логічні помилки та граничні випадки відносно вимог:**
   - **Рядки 42–43 (`GET /api/students/:id/card`):** якщо у студента немає оцінок, у картку підставляється результат `averageGrade` (`NaN` або `null`), тоді як вимога передбачає виведення тексту `«оцінок немає»`.
   - **Спосіб виправлення:** перевіряти `const avgText = avg === null ? "оцінок немає" : avg;` перед формуванням HTML.
   - **Рядок 47 (`DELETE /api/students/:id`) *(зауваження потребує перевірки тестом → хибне спрацювання)*:** перед викликом `students.deleteStudent(db, req.studentId)` немає окремого виклику `students.getById`, тому треба перевірити, чи коректно повертається `404` для неіснуючого студента. *(Перевірка тестом показала, що `deleteStudent` повертає `changes > 0`, отже `404` повертається коректно).*

## 2. Аналіз файлу `src/students.js`

1. **Обробка вхідних даних від користувача:**
   - **Рядки 17, 22, 28 (`getById`, `averageGrade`, `deleteStudent`) *(хибне спрацювання через ізольований огляд файлу)*:** функції не перевіряють, чи є `id` додатним цілим числом. *(Насправді цю перевірку вже виконує проміжний обробник `validateId` у `src/app.js`).*

2. **Формування запитів до бази даних:**
   - **Рядки 11–15 (`findByName`):** SQL-запит формується конкатенацією рядків: `"SELECT id, name, group_name FROM students WHERE name LIKE '%" + name + "%'"`. Крім того, символи `%` та `_` у параметрі `name` не екрануються для оператора `LIKE`.
   - **Можливий наслідок:**
     1) **SQL-ін’єкція (OWASP A05:2025):** передача `%' OR 1=1 --` дозволяє обійти фільтр і вивантажити всі записи або виконати підзапит.
     2) **Збій сервера (500) на імені з апострофом:** передача імені на кшталт `Лук'ян` ламає синтаксис SQL-рядка, що порушує вимогу «будь-які символи в `name` (зокрема апостроф) обробляються як звичайний текст».
     3) **Некоректний пошук символу `%`:** пошук за `%` поверне всіх студентів замість тих, чиє ім’я реально містить символ `%`.
   - **Спосіб виправлення:** екранувати спецсимволи `LIKE` (`const escaped = String(name).replace(/[\\%_]/g, "\\$&");`) і використовувати параметризований запит `WHERE name LIKE ? ESCAPE '\\'` із параметром `` `%${escaped}%` ``.

3. **Перевірка автентифікації та прав доступу:**
   - Проблем немає (рівень доступу до даних не відповідає за HTTP-автентифікацію).

4. **Зберігання паролів і секретів:**
   - Проблем немає.

5. **Обробка помилок і те, що потрапляє у відповідь користувачу:**
   - Проблем немає (помилки SQL виникали лише через неекранований апостроф у `findByName`).

6. **Логічні помилки та граничні випадки відносно вимог:**
   - **Рядок 7 (`listStudents`):** вираз `rows.slice(start, start + PAGE_SIZE - 1)` при `PAGE_SIZE = 5` повертає лише **4** студенти замість **5** (помилка «на одиницю» / off-by-one).
   - **Можливий наслідок:** порушення вимоги «Сторінка з 5 студентів, `page` починається з 1».
   - **Спосіб виправлення:** змінити зріз на `rows.slice(start, start + PAGE_SIZE)`.
   - **Рядки 22–26 (`averageGrade`):** якщо студент не має жодної оцінки (`rows.length === 0`), вираз `sum / rows.length` виконує ділення `0 / 0` і повертає `NaN` замість `null`.
   - **Можливий наслідок:** порушення вимоги «для студента без оцінок — `{ average: null }`» (у HTML-картці перетворюється на рядок `"NaN"`).
   - **Спосіб виправлення:** додати перевірку `if (rows.length === 0) return null;` перед обчисленням суми.

## 3. Аналіз файлу `src/auth.js`

1. **Обробка вхідних даних від користувача:**
   - **Рядки 4, 37 (`hashPassword`, `login`):** якщо в `POST /api/login` передати порожнє тіло або не передати `password` (`undefined`), виклик `crypto.createHash("md5").update(undefined)` викине виняток `TypeError`, що призведе до відповіді `500` замість `401`.
   - **Спосіб виправлення:** перевіряти `if (typeof loginName !== "string" || typeof password !== "string") return null;` на початку `login()`.

2. **Формування запитів до бази даних:**
   - Проблем немає (`SELECT login, password_hash, role FROM users WHERE login = ?` використовує параметризований запит `?`).

3. **Перевірка автентифікації та прав доступу:**
   - **Рядки 13–26 (`createToken`, `verifyToken`) *(хибне спрацювання)*:** токен не є стандартним JWT і не має поля `exp`. *(Для навчального проєкту структура `login.role.підпис` із HMAC-SHA256 та `crypto.timingSafeEqual` є коректною і відповідає вимогам).*

4. **Зберігання паролів і секретів:**
   - **Рядки 4–6 (`hashPassword`) та рядок 39 (`login`):** паролі гешуються алгоритмом MD5 без солі (`crypto.createHash("md5").update(password).digest("hex")`).
   - **Можливий наслідок:** криптографічний збій (OWASP A04:2025) — MD5 не має солі й обчислюється мільярдами комбінацій за секунду, що дозволяє миттєво відновити паролі за райдужними таблицями. Порушено вимогу «Паролі зберігаються лише як стійкий геш із сіллю».
   - **Спосіб виправлення:** використати `crypto.randomBytes(16)` для генерації унікальної солі та `crypto.scryptSync(password, salt, 64)` для отримання стійкого гешу у форматі `salt:hash`, а перевірку виконувати через `crypto.timingSafeEqual`.

5. **Обробка помилок і те, що потрапляє у відповідь користувачу:**
   - Проблем немає (повертається узагальнене `401 Потрібна автентифікація`).

6. **Логічні помилки та граничні випадки відносно вимог:**
   - Проблем немає (окрім перевірки типів `loginName` і `password`).
